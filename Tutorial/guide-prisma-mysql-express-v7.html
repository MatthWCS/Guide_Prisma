💡 Pourquoi tsx et pas ts-node ? ▼
ts-node est l'outil historique pour exécuter TypeScript directement dans Node.js. Il a deux problèmes avec l'architecture moderne :

  • Il gère mal ESM (ECMAScript Modules), le système import/export moderne.
  • Il est lent car il transpile à la volée via le compilateur TypeScript officiel.

tsx est un remplacement moderne basé sur esbuild (le même moteur que Vite). Il est beaucoup plus rapide et supporte ESM nativement. Pour exécuter un script : npx tsx script.ts. Pour le mode watch (rechargement auto) : tsx watch src/index.ts.

03
Configurer ESM
ECMAScript Modules — le système import/export moderne

Prisma v7 adopte ESM par défaut. ESM est le système de modules standardisé de JavaScript, qui utilise import/export au lieu de require/module.exports (CommonJS). Deux fichiers à modifier :

tsconfig.json

📄 tsconfig.json — remplacer le contenu généré par npx tsc --init
json 
{
  "compilerOptions": {
    "module":             "ESNext",
    "moduleResolution":   "bundler",
    "target":             "ES2023",
    "lib":                ["ES2023"],
    "types":              ["node"],        // ← indispensable pour process, __dirname…
    "strict":             true,
    "esModuleInterop":    true,
    "ignoreDeprecations": "6.0"
  }
}

package.json — ajouter "type": "module"

📄 package.json — ajouter la ligne type + scripts
json 
{
  "name": "mon-api",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    "dev":          "tsx watch src/index.ts",
    "build":        "tsc",
    "start":        "node dist/index.js",
    "db:migrate":   "prisma migrate dev",
    "db:generate":  "prisma generate",
    "db:studio":    "prisma studio"
  }
}
🔍 Explication ligne par ligne du tsconfig ▼
"types": ["node"] Indique à TypeScript de charger les déclarations de types Node.js (process, Buffer, __dirname…). Sans cette option, TypeScript ne connaît pas process.env et souligne tous tes accès aux variables d'environnement en rouge.
"lib": ["ES2023"] Déclare quelles API JavaScript natives sont disponibles au runtime (Promise, Map, Set, Array methods…). Doit correspondre au target.
"module": "ESNext" TypeScript compile vers ESM (utilise import/export dans le JS généré). Sans cette option, il compilerait vers CommonJS (require).
"moduleResolution": "bundler" Algorithme de résolution des imports. "bundler" est le mode moderne, compatible avec tsx et esbuild. L'ancien mode "node" ne comprend pas certains imports ESM modernes.
"target": "ES2023" La version de JavaScript produite. ES2023 est supportée par Node.js 20+.
"ignoreDeprecations": "6.0" Supprime certains warnings TypeScript liés à des options dépréciées dans TS 6.0. Recommandé par la doc officielle Prisma.
"type": "module" (package.json) Indique à Node.js que tous les fichiers .js de ce projet sont ESM. Sans cette ligne, Node.js traite les .js comme CommonJS même si ton TypeScript compile vers ESM.

Initialiser Prisma ORM
Création du schéma, de la config et du .env
📟 Terminal
bash 
npx prisma init --datasource-provider mysql --output ../generated/prisma
🔍 Que fait cette commande ? (3 fichiers créés) ▼
Cette commande crée trois choses :
prisma/schema.prisma Le fichier central : il décrit tes modèles de données (tables, colonnes, relations). C'est la source de vérité.
.env Fichier de variables d'environnement. Contient l'URL de connexion MySQL. Ne jamais le committer dans Git.
prisma.config.ts ← nouveau v7 Fichier de configuration Prisma externalisé. Centralise le chemin du schéma, des migrations et l'URL de connexion. Remplace ce qui était dans schema.prisma.

L'option --output ../generated/prisma indique où générer le client Prisma. En v7, il atterrit dans generated/prisma/ à la racine du projet plutôt que dans node_modules/@prisma/client. Avantages : le code est visible, inspectable, et tu l'importes avec un chemin relatif clair.

❓ Pourquoi deux façons d'écrire les credentials ? ▼
Il y a deux consommateurs distincts avec des besoins différents :

DATABASE_URL (format URL) — utilisée par la CLI Prisma (prisma migrate, prisma studio…) quand elle doit se connecter à la base. La CLI lit prisma.config.ts qui utilise env("DATABASE_URL").

Variables séparées HOST/PORT/USER… — utilisées par le Driver Adapter dans ton code TypeScript. Le constructeur new PrismaMariaDb({ host, user, password... }) attend des paramètres distincts, pas une URL. C'est l'API du driver @prisma/adapter-mariadb.

Les deux doivent pointer vers la même base, avec les mêmes credentials.
⚠️
Ajoute .env à ton .gitignore immédiatement. Ne committe jamais tes credentials de base de données.

AttributSQL généréExplication

@default(autoincrement())AUTO_INCREMENTValeur entière auto-incrémentée à chaque INSERT.

Schéma étendu pour un blog complet

Pour un projet réel, on ajoute des types plus précis, des timestamps et une relation N-à-M :

📄 prisma/schema.prisma — schéma de blog complet
Prisma 
generator client {
  provider = "prisma-client"
  output   = "../generated/prisma"
}

datasource db {
  provider = "mysql"
}

enum Role {
  USER
  ADMIN
}

model User {
  id        Int      @id @default(autoincrement())
  email     String   @unique
  name      String?  @db.VarChar(100)
  password  String   @db.VarChar(255)
  role      Role     @default(USER)
  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @updatedAt      @map("updated_at")
  posts     Post[]
  @@map("users")
}

model Post {
  id        Int      @id @default(autoincrement())
  title     String   @db.VarChar(255)
  slug      String   @unique @db.VarChar(255)
  content   String?  @db.LongText
  published Boolean  @default(false)
  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @updatedAt      @map("updated_at")
  authorId  Int      @map("author_id")
  author    User     @relation(fields: [authorId], references: [id])
  tags      Tag[]
  @@map("posts")
}

model Tag {
  id    Int    @id @default(autoincrement())
  name  String @unique @db.VarChar(50)
  posts Post[]               // relation N-à-M implicite avec Post
  @@map("tags")
}

⚙️ Que fait prisma migrate dev exactement ? ▼
En une seule commande, Prisma fait 3 choses dans l'ordre :
① Génère le SQL Compare ton schema.prisma avec l'état actuel de la base. Calcule le diff et génère un fichier prisma/migrations/20240101_init/migration.sql.
② Exécute le SQL Applique le fichier SQL sur ta base MySQL. Crée les tables, colonnes, index, foreign keys…
③ Génère le client Appelle prisma generate automatiquement. Le dossier generated/prisma/ est mis à jour avec les types TypeScript correspondant à tes nouveaux modèles.

    `email`      VARCHAR(191) NOT NULL,
    `name`       VARCHAR(191),

    `created_at` DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),

07
Instancier Prisma Client
Driver Adapter + singleton + variables d'environnement

C'est le fichier que tu avais en screenshot avec les soulignements rouges. Voici la version correcte avec la gestion propre des variables d'environnement.

📄 src/lib/prisma.ts — version officielle + correction des types
TypeScript 
import "dotenv/config"
import { PrismaMariaDb } from "@prisma/adapter-mariadb"
import { PrismaClient }  from "../../generated/prisma/client"

// ── Validation des variables d'env au démarrage ──────────────────
// Évite les erreurs silencieuses : si une var manque, on le sait immédiatement
function requireEnv(key: string): string {
  const value = process.env[key]
  if (!value) throw new Error(`Variable manquante dans .env : ${key}`)
  return value
}

// ── Driver Adapter : gère la connexion TCP avec MySQL ────────────
const adapter = new PrismaMariaDb({
  host:            requireEnv("DATABASE_HOST"),
  user:            requireEnv("DATABASE_USER"),
  password:        requireEnv("DATABASE_PASSWORD"),
  database:        requireEnv("DATABASE_NAME"),
  port:            Number(process.env.DATABASE_PORT) || 3306,
  connectionLimit: 5,   // max connexions simultanées dans le pool
})

// ── Prisma Client : API de requêtes TypeScript ───────────────────
const prisma = new PrismaClient({ adapter })

export { prisma }
🔴 Pourquoi les soulignements rouges et comment les corriger ▼
Cause principale : process.env.X retourne string | undefined en TypeScript. Or, PrismaMariaDb attend des string stricts. TypeScript refuse la combinaison.

La fonction requireEnv() résout le problème : elle vérifie que la valeur existe (if (!value) throw), puis retourne un string garanti. TypeScript est satisfait.

Pour le port : process.env.DATABASE_PORT est toujours une string, on le convertit avec Number(). Le || 3306 fournit une valeur par défaut si la variable est absente.

Avantage bonus : si tu oublies de définir une variable dans .env, ton serveur plante immédiatement au démarrage avec un message clair — pas à la première requête en production.
🔍 Qu'est-ce qu'un Driver Adapter et pourquoi ça change en v7 ? ▼
Prisma v5 et avant : Prisma embarquait un moteur en Rust qui gérait lui-même la connexion TCP à MySQL, la sérialisation des requêtes et le pool de connexions. Ce moteur était opaque, difficile à configurer et produisait un binaire natif lourd.

Prisma v7 : Prisma délègue à un Driver Adapter — une couche Node.js pure qui utilise un driver de la communauté (ici le driver MariaDB/MySQL). Tu passes cet adapter à PrismaClient({ adapter }).

Avantages :
  • Tu contrôles le pool de connexions (connectionLimit).
  • Le client est plus léger (pas de binaire natif).
  • Compatible avec les environnements Edge (Cloudflare Workers, etc.).
  • Meilleure interopérabilité avec l'écosystème Node.js.
connectionLimit: 5 signifie que Prisma maintient au maximum 5 connexions TCP ouvertes vers MySQL en parallèle. Les requêtes supplémentaires attendent qu'une connexion se libère.
🔍 Pourquoi l'import vient de ../../generated/prisma/client ? ▼
En Prisma v7 avec l'option --output ../generated/prisma, le client généré atterrit dans generated/prisma/ à la racine du projet.

Si ton fichier est dans src/lib/prisma.ts, le chemin relatif vers generated/prisma/client est ../../generated/prisma/client (deux niveaux vers le haut).

Structure :
src/lib/prisma.ts → ../ remonte dans src/ → ../../ remonte à la racine → generated/prisma/client
Si ton fichier était dans src/prisma.ts, le chemin serait ../generated/prisma/client. Ajuste selon ton arborescence.

import { prisma } from "./src/lib/prisma.js"

async function main() {
  // Créer un utilisateur avec un post lié en une seule requête
  const user = await prisma.user.create({
    data: {
      name:  "Alice",
      email: "alice@prisma.io",
      posts: {
        create: {
          title:     "Hello World",
          content:   "Mon premier post avec Prisma !",
          published: true,
        },
      },
    },
    include: {
      posts: true,   // retourner les posts dans la réponse
    },
  })
  console.log("Utilisateur créé :", user)

  // Lire tous les utilisateurs avec leurs posts
  const allUsers = await prisma.user.findMany({
    include: { posts: true },
  })
  console.log("Tous les utilisateurs :", JSON.stringify(allUsers, null, 2))
}

main()
  .then(async () => { await prisma.$disconnect() })
  .catch(async (e) => {
    console.error(e)
    await prisma.$disconnect()
    process.exit(1)
  })

📄 Toutes les méthodes Prisma Client
TypeScript 
import { prisma } from "./src/lib/prisma.js"

// ── CREATE ───────────────────────────────────────────────────────
const newUser = await prisma.user.create({
  data: { email: "bob@exemple.fr", name: "Bob" },
})

// ── READ ONE (par champ unique) ───────────────────────────────────
const user = await prisma.user.findUnique({
  where: { email: "bob@exemple.fr" },
})
// Si l'enregistrement doit exister (lève une erreur si absent) :
const userOrThrow = await prisma.user.findUniqueOrThrow({
  where: { id: 1 },
})

// ── READ MANY (filtre + tri + pagination) ─────────────────────────
const users = await prisma.user.findMany({
  where:   { name: { contains: "bob" } },
  orderBy: { createdAt: "desc" },
  take:    10,      // LIMIT 10
  skip:    0,       // OFFSET 0
  select:  { id: true, email: true, name: true }, // pas de password !
})

// ── UPDATE ───────────────────────────────────────────────────────
const updated = await prisma.user.update({
  where: { id: 1 },
  data:  { name: "Bob Dupont" },
})

// ── UPSERT (créer si absent, mettre à jour si présent) ───────────
const upserted = await prisma.user.upsert({
  where:  { email: "alice@exemple.fr" },
  update: { name: "Alice Updated" },
  create: { email: "alice@exemple.fr", name: "Alice" },
})

// ── DELETE ───────────────────────────────────────────────────────
await prisma.user.delete({ where: { id: 1 } })

// ── COUNT ────────────────────────────────────────────────────────
const total = await prisma.post.count({
  where: { published: true },
})

// ── AGGREGATE (stats numériques) ─────────────────────────────────
const stats = await prisma.post.aggregate({
  _count: { id: true },
  _avg:   { id: true },
})

// ── FILTRES AVANCÉS ───────────────────────────────────────────────
const posts = await prisma.post.findMany({
  where: {
    AND: [
      { published: true },
      { title: { contains: "prisma" } },
      { createdAt: { gte: new Date("2024-01-01") } },
    ],
  },
})

Charger les données liées — JOIN sans écrire de SQL
📄 Requêtes avec relations
TypeScript 
// ── include : charger les relations (comme un JOIN) ───────────────
const userWithPosts = await prisma.user.findUnique({
  where:   { id: 1 },

    },
  },
})

// ── Créer un post lié à un user existant ──────────────────────────
const post = await prisma.post.create({
  data: {
    title:   "Mon article",
    content: "Contenu...",
    author:  { connect: { id: 1 } },  // relier à l'user id=1
  },
  include: { author: true },
})

// ── _count : compter les relations sans les charger ───────────────
const usersWithCount = await prisma.user.findMany({
  select: {
    id:     true,
    email:  true,
    _count: { select: { posts: true } },  // nb de posts sans les charger
  },
})

// ── Transaction : plusieurs opérations atomiques ──────────────────
const [usersResult, postsResult] = await prisma.$transaction([
  prisma.user.findMany(),
  prisma.post.count({ where: { published: true } }),
])

// ── Transaction interactive (dépendances entre opérations) ────────
const result = await prisma.$transaction(async (tx) => {
  const user = await tx.user.create({ data: { email: "x@x.fr" } })
  const post = await tx.post.create({
    data: { title: "Post", author: { connect: { id: user.id } } },
  })
  return { user, post }   // si ça plante ici, les deux sont annulés
})
⚡
Problème N+1 : ne jamais appeler findMany() dans une boucle. Utilise include ou _count pour charger les relations en une seule requête SQL. Prisma génère un JOIN efficace automatiquement.

Architecture MVC — Vue d'ensemble
Route → Controller → Model : séparation claire des responsabilités

Mettre toute la logique directement dans les routes est une erreur fréquente qui rend le code difficile à tester et à maintenir. L'architecture MVC sépare les responsabilités en trois couches :

CoucheFichiersResponsabilité
Routesrc/routes/*.tsDéclare les endpoints HTTP. Ne fait rien d'autre que d'appeler le bon controller. Aucune logique ici.
Controllersrc/controllers/*.tsValide les entrées (req.body, req.params), appelle le model, formate la réponse HTTP. C'est la logique métier.
Modelsrc/models/*.tsToutes les requêtes Prisma. Retourne des données brutes. Aucune référence à Express (req, res) ici.

Point d'entrée Express

📄 src/index.ts
TypeScript 
import express from "express"
import { usersRouter } from "./routes/users.js"
import { postsRouter }  from "./routes/posts.js"
import { tagsRouter }   from "./routes/tags.js"
import { errorHandler } from "./middleware/errorHandler.js"

const app  = express()
const PORT = Number(process.env.PORT) || 3000

app.use(express.json())

// Routes — chaque router gère son préfixe
app.use("/api/users", usersRouter)
app.use("/api/posts",  postsRouter)
app.use("/api/tags",   tagsRouter)

// Healthcheck
app.get("/health", (_req, res) => {
  res.json({ status: "ok", timestamp: new Date().toISOString() })
})

// 404 et gestionnaire d'erreurs global (toujours en dernier)

  console.log(`🚀 Serveur sur http://localhost:${PORT}`)

import { prisma } from "../lib/prisma.js"

type PostCreateInput = {
  title:    string
  content?: string
  slug:     string
  authorId: number
  tagIds?:  number[]
}

type PostUpdateInput = {
  title?:     string
  content?:   string
  published?: boolean
  tagIds?:    number[]
}

const postInclude = {
  author: { select: { id: true, name: true, email: true } },
  tags:   { select: { id: true, name: true } },
} as const

export const PostModel = {

  findAll: (page: number, limit: number, published?: boolean) => {
    const skip  = (page - 1) * limit
    const where = published !== undefined ? { published } : {}
    return prisma.$transaction([
      prisma.post.findMany({
        where, skip, take: limit,
        include: postInclude,
        orderBy: { id: "desc" },
      }),
      prisma.post.count({ where }),
    ])
  },

  findById: (id: number) =>
    prisma.post.findUnique({ where: { id }, include: postInclude }),

  findBySlug: (slug: string) =>
    prisma.post.findUnique({ where: { slug }, include: postInclude }),

  create: ({ tagIds, ...data }: PostCreateInput) =>
    prisma.post.create({
      data: {
        ...data,
        tags: tagIds?.length
          ? { connect: tagIds.map((id) => ({ id })) }
          : undefined,
      },
      include: postInclude,
    }),

  update: (id: number, { tagIds, ...data }: PostUpdateInput) =>
    prisma.post.update({
      where: { id },
      data: {
        ...data,
        tags: tagIds !== undefined
          ? { set: tagIds.map((id) => ({ id })) }  // set remplace les tags existants
          : undefined,
      },
      include: postInclude,
    }),

  remove: (id: number) =>
    prisma.post.delete({ where: { id } }),

  countByAuthor: (authorId: number) =>
    prisma.post.count({ where: { authorId } }),

}

Couche Controllers — Logique métier
Validation des entrées, appel du model, formatage de la réponse

Le controller est le chef d'orchestre : il reçoit la requête HTTP d'Express, valide les données, appelle le model, puis renvoie la réponse. Il ne contient aucune requête Prisma directe. En cas d'erreur, il appelle next(err) pour déléguer au middleware d'erreur.

user.controller.ts

📄 src/controllers/user.controller.ts
TypeScript 
import { Request, Response, NextFunction } from "express"
import { UserModel } from "../models/user.model.js"

export const UserController = {

  getAll: async (req: Request, res: Response, next: NextFunction) => {
    try {
      const page  = Math.max(1, Number(req.query.page)  || 1)
      const limit = Math.min(100, Number(req.query.limit) || 10)
      const [data, total] = await UserModel.findAll(page, limit)
      res.json({ data, pagination: { page, limit, total, pages: Math.ceil(total / limit) } })
    } catch (err) { next(err) }
  },

  getOne: async (req: Request, res: Response, next: NextFunction) => {
    try {
      const id = parseInt(req.params.id)
      if (isNaN(id)) return res.status(400).json({ error: "ID invalide" })
      const user = await UserModel.findById(id)
      if (!user) return res.status(404).json({ error: "Utilisateur introuvable" })
      res.json(user)
    } catch (err) { next(err) }
  },

  create: async (req: Request, res: Response, next: NextFunction) => {
    try {
      const { email, name, password } = req.body
      if (!email || !password)
        return res.status(400).json({ error: "email et password sont requis" })
      // Note : hasher le password ici avec bcrypt avant de passer au model
      const user = await UserModel.create({ email, name, password })
      res.status(201).json(user)
    } catch (err) { next(err) }
  },

  update: async (req: Request, res: Response, next: NextFunction) => {
    try {
      const id = parseInt(req.params.id)
      if (isNaN(id)) return res.status(400).json({ error: "ID invalide" })
      const user = await UserModel.update(id, { name: req.body.name })
      res.json(user)
    } catch (err) { next(err) }
  },

  remove: async (req: Request, res: Response, next: NextFunction) => {
    try {
      const id = parseInt(req.params.id)
      if (isNaN(id)) return res.status(400).json({ error: "ID invalide" })
      await UserModel.remove(id)
      res.status(204).send()
    } catch (err) { next(err) }
  },

}

Gestion des erreurs Prisma
Intercepter les erreurs typées et retourner les bons codes HTTP
📄 src/middleware/errorHandler.ts
TypeScript 
import { Request, Response, NextFunction } from "express"
import { Prisma } from "../../generated/prisma/client"

export function errorHandler(
  err: Error,
  _req: Request,
  res: Response,
  _next: NextFunction,
) {
  console.error(err)

  // Erreur Prisma connue (contrainte, not found, FK…)
  if (err instanceof Prisma.PrismaClientKnownRequestError) {
    switch (err.code) {
      case "P2002":   // contrainte unique violée
        return res.status(409).json({
          error: "Conflit : valeur déjà utilisée",
          field: (err.meta?.target as string[])?.join(", "),
          code:  err.code,
        })
      case "P2025":   // enregistrement introuvable (update/delete)
        return res.status(404).json({ error: "Ressource introuvable", code: err.code })
      case "P2003":   // violation de clé étrangère
        return res.status(400).json({ error: "Référence invalide", code: err.code })
      default:
        return res.status(400).json({ error: err.message, code: err.code })
    }
  }

  // Erreur de validation (mauvais type de données)
  if (err instanceof Prisma.PrismaClientValidationError) {
    return res.status(400).json({ error: "Données invalides" })
  }

  // Erreur générique
  res.status(500).json({
    error: "Erreur interne du serveur",
    ...(process.env.NODE_ENV === "development" && { details: err.message }),
  })
}

Bonnes pratiques
Sécurité, performance et maintenabilité
🔐
Ne jamais retourner le mot de passe. Utilise toujours select: { password: false } ou liste explicitement les champs à retourner. Par défaut, Prisma retourne tous les champs.
⚡
Évite le problème N+1. Si tu fais findMany() puis une boucle avec findUnique() pour chaque résultat, tu génères N+1 requêtes SQL. Utilise include ou _count à la place.
🗄️
Versionne tes migrations. Le dossier prisma/migrations/ doit être committé dans Git. C'est l'historique de l'évolution de ta base — indispensable pour la prod et le travail en équipe.
🏭
En production, utilise prisma migrate deploy (pas migrate dev). La commande deploy est non-interactive et ne génère pas de nouvelles migrations — elle applique seulement celles qui existent déjà.
🔄
Après git pull sur un projet existant, toujours exécuter npx prisma generate pour s'assurer que le client TypeScript est synchronisé avec le schéma de tes collègues.
